1. INTRODUCTION
================================================================================

1.1 Purpose

This document provides a comprehensive system analysis and design for the Pharmacy Stock & Expiry Tracker Real-Time Application. It serves as the technical blueprint for development, detailing the system architecture, database design, process flows, interface specifications, and implementation guidelines. The document translates the requirements captured in the Software Requirements Specification (SRS) into a structured technical design that guides the development team.

1.2 Scope

The Pharmacy Stock & Expiry Tracker is a web-based real-time application designed for pharmacy inventory and financial management. The system supports three distinct user roles: Customers, Shop Owners, and Super Admin (Supplier). It provides comprehensive functionality including real-time inventory management, expiry tracking with vendor-wise replacement requests, alternative medicine suggestions powered by Aura DB, financial reporting with revenue and profit analytics, supply management with PDF generation, and role-based access control. The system integrates with MongoDB Atlas as the primary data store and Aura DB for alternative medicine suggestion logic.

2. SYSTEM OVERVIEW
================================================================================

2.1 Product Perspective

The Pharmacy Stock & Expiry Tracker is a standalone web-based real-time application built on a three-tier architecture: presentation layer (React.js frontends), application layer (Node.js/Express.js backend), and data layer (MongoDB Atlas + Aura DB). The system follows a microservices-inspired modular design where each functional domain (inventory, orders, users, vendors, reports, etc.) is implemented as a separate controller and route module, communicating through well-defined RESTful and GraphQL APIs. The frontend consists of two separate Single Page Applications: an Admin Frontend for Super Admin operations and an Owner Frontend for Shop Owner and Customer operations.

2.2 User Roles and Characteristics

The system defines three primary user roles with distinct capabilities:

Customer: Self-registers on the platform, searches inventory by medicine type (Tablets, Capsules, Syrups, Suspensions, Sachets, Creams) and medical system (Allopathy, Homeopathy, Ayurvedic), receives alternative medicine suggestions when requested items are out of stock, gets notified when medicines are unavailable, manages own profile, orders, shopping cart, and notifications. Customers have read-only access to medicine catalog and can only access their own data.

Shop Owner: Registered by Super Admin, manages inventory (full CRUD on medicines within their shop), monitors expiry dates, generates expired medicines lists and vendor-wise replacement requests, generates financial reports (revenue, profit, vendor-wise payments, customer-wise payments) for Day/Week/Month/Year periods, registers and manages suppliers/vendors, processes customer orders, enters supply details with PDF generation, manages shop profile. Shop Owners operate within their assigned shop context (shopId) and cannot access other shops' data.

Super Admin (Supplier): Registers shop owners and shop details, manages system-wide users (CRUD on all user accounts with role assignment), manages system-wide vendors, configures system settings, views system-wide analytics and platform health metrics. Super Admin has full system access across all shops but typically does not manage day-to-day inventory operations.

2.3 Operating Environment

Frontend: Modern web browsers with JavaScript ES6+ support. React.js 18.2 with Vite 4.3 build tool. Responsive design using Bootstrap 5.2.3 with Framer Motion animations.

Backend: Node.js runtime with Express.js 4.18 framework. RESTful and GraphQL API support. JWT-based authentication with bcryptjs password hashing.

Database: MongoDB Atlas (primary) for inventory, users, transactions, reports, expiry logs, alternatives, notifications, and supplies. Aura DB (graph database) for alternative medicine suggestion engine and related data.

External Services: PDF generation via pdfkit library. Email service integration for notifications (planned).

2.4 System Constraints

- Code Number on medicines must be unique and not null (enforced at API level)
- Manufacture Date must be earlier than or equal to Expiry Date
- Supply entries require valid medicineId and supplierId references
- Vendor-wise replacement requests restricted to Shop Owner's own shop medicines
- Customer self-registration is open; Shop Owner and Super Admin accounts require admin creation
- Shop Owners can only manage data within their own shop (shopId isolation)
- Real-time updates required for stock levels, expiry status, and notifications
- Page load times must not exceed 3 seconds under normal network conditions
- Database queries for reports must complete within 5 seconds
- System must maintain 99.5% uptime during business hours
- All API communications must use HTTPS
- Future migration to Java-based backend must be supported without major re-architecture

3. REQUIREMENTS ANALYSIS
================================================================================

3.1 Functional Requirements

3.1.1 Inventory Management
The system shall allow shop owners to maintain minimal inventory per item supporting Just-In-Time (JIT) philosophy. Real-time stock level tracking for all medicines with automatic quantity updates upon sales and purchases. Medicines classified by type (Tablets, Capsules, Syrups, Suspensions, Sachets, Creams) with appropriate quantity units (grams for tablets/sachets/creams, ml for syrups/suspensions, count for tablets/capsules). Classification by medical system (Allopathy, Homeopathy, Ayurvedic) with filtering and searching capabilities.

3.1.2 Expiry Tracking
Continuous monitoring of expiry dates for all inventory items. Generation of expired medicines list upon shop owner command. Vendor-wise list of expired items to facilitate replacement requests from vendors. Replacement request tracking with status management.

3.1.3 Alternative Medicine Suggestions
When a customer requests an out-of-stock medicine, the system queries Aura DB for available alternatives with similarity scoring. If no alternatives available, appropriate message displayed to customer. Alternative suggestions include availability status.

3.1.4 Notifications
Automatic notification generation when customer searches for medicine not found in inventory and no alternatives available. Customers receive notifications through application interface with read/unread status management.

3.1.5 Financial Reporting
Revenue and profit reports for configurable periods (Day, Week, Month, Year). Vendor-wise payment reports for selected period. Customer-wise payment reports for selected period. PDF export capability for all reports.

3.1.6 User Management
Role-based access control for three user roles. Secure token-based authentication. Customer self-registration with email validation. Shop owner registration exclusively by Super Admin. Supplier registration by Shop Owner after creation by Super Admin.

3.1.7 Supply Management
Supply entry recording with code number, quantity, batch number, expiry date, supplier ID. Automatic inventory quantity update upon supply entry. Shareable PDF generation for suppliers with item details, batch numbers, expiry dates, supplier information.

3.2 Non-Functional Requirements

3.2.1 Performance
Real-time updates for stock levels and expiry status. Page load times under 3 seconds. Report queries under 5 seconds. Efficient database indexing strategy.

3.2.2 Security
HTTPS for all API communications. JWT-based authentication with secure token mechanisms. Role-based access control restricting data access by role. Password hashing with bcryptjs. Input validation with express-validator.

3.2.3 Reliability
99.5% uptime during business hours. Automated scheduled data backups. Error handling with structured response format.

3.2.4 Maintainability
Modular architecture with separate controllers, routes, models, and middleware. Clear separation of concerns. Future Java backend migration supported.

3.3 Use Case Analysis

The system implements 25 use cases distributed across three actors:

Customer (6 use cases): Search Medicines, Purchase Medicine, View Alternative Medicines (extends Search), Receive Out-of-Stock Notification (extends View Alternatives), Customer Self-Registration, Update Profile, Cancel Order, Manage Cart.

Shop Owner (12 use cases): Manage Inventory, Track Expiry Dates, Generate Expired Medicines List, Request Replacement from Vendor (extends Generate Expired List), Generate Revenue & Profit Report, View Vendor-wise Payments, View Customer-wise Payments, Manage Vendors, Enter New Supply, Generate Supplier PDF (extends Enter New Supply), Register Supplier, Update Shop Profile, Cancel/Void Orders.

Super Admin (4 use cases): Manage Vendors (system-wide), Manage Users & Roles, View System Analytics, Manage Shops, Update System Settings.

Key extend relationships: Alternative suggestions extend search; notifications extend alternatives; replacement requests extend expired list; supplier PDF extends supply entry.

4. SYSTEM ARCHITECTURE
================================================================================

4.1 Architectural Style

The system follows a layered three-tier architecture with modular domain-driven design:

Presentation Layer: Two React.js SPAs (Admin Frontend, Owner Frontend) communicating with backend via REST/GraphQL APIs. Component-based UI with state management through React hooks and context.

Application Layer: Node.js/Express.js backend organized by functional domains. Each domain has dedicated routes, controllers, models, and validation middleware. Shared middleware for authentication, error handling, and response formatting. Service layer pattern for business logic separation.

Data Layer: MongoDB Atlas (document database) for primary persistence with Mongoose ODM. Aura DB (graph database) for alternative medicine relationships. PDF generation service as external utility.

Communication: RESTful APIs for standard CRUD operations. GraphQL endpoints for flexible real-time querying. Asynchronous processing for PDF generation and notifications.

5. DATABASE DESIGN
================================================================================

5.1 Conceptual Data Model (ERD)

The Entity Relationship Diagram defines 8 core entities with relationships:

USERS: Central entity for all user types (Customer, Shop Owner, Super Admin). Attributes: _id, name, email, passwordHash, role, phone, address, isActive, createdAt, updatedAt.

MEDICINES: Core inventory entity. Attributes: _id, name, genericName, category, manufacturer, supplierId, batchNumber, expiryDate, quantityInStock, minStockLevel, pricePerUnit, costPrice, description, isActive, createdAt, updatedAt. Relationships: supplied by VENDOR, ordered in ORDER_ITEMS, tracked in EXPIRY_LOGS, has ALTERNATIVE.

VENDORS: Supplier management. Attributes: _id, name, contactPerson, email, phone, address, gstNumber, isActive, createdAt, updatedAt. Relationships: supplies MEDICINES, receives VENDOR_PAYMENTS, replacement for EXPIRY_LOGS.

ORDERS: Customer purchase orders. Attributes: _id, customerId, totalAmount, paymentStatus, orderStatus, orderDate, updatedAt. Contains ORDER_ITEMS (embedded array).

ORDER_ITEMS: Line items within orders. Attributes: _id, orderId, medicineId, medicineName, quantity, unitPrice, totalPrice.

PAYMENTS: Financial transactions. Attributes: _id, vendorId, userId, amount, paymentMethod, paymentStatus, paymentDate, notes, createdAt.

EXPIRY_LOGS: Expired medicine tracking. Attributes: _id, medicineId, supplierId, medicineName, quantityExpired, expiryDate, replacementRequested, replacementDate, status, createdAt.

ALTERNATIVES (Aura DB): Alternative medicine suggestions. Attributes: _id, originalMedicineId, alternativeMedicineId, alternativeName, similarityScore, isAvailable, createdAt.

5.2 Logical Data Model

Collections mapped to MongoDB document structure with references and embedding:

Users Collection: Single collection for all roles differentiated by 'role' field. Address embedded as sub-document.

Medicines Collection: Primary inventory collection. Supplier reference via supplierId. Indexes on supplierId, expiryDate, text search on name/genericName, quantityInStock.

Suppliers/Vendors Collection: Vendor management with GST number. Address embedded.

Orders Collection: Customer orders with embedded ORDER_ITEMS array for atomic order operations. References to customerId.

Payments Collection: Tracks all financial transactions with vendorId and userId references.

ExpiryLogs Collection: Audit trail for expired medicines with supplier reference for replacement workflow.

Alternatives Collection (Aura DB): Graph-based relationships between original and alternative medicines with similarity scoring.

5.3 Physical Data Model

MongoDB Atlas collections with indexing strategy:

Users: Unique index on email, index on role.
Medicines: Index on supplierId, expiryDate, compound text index on name+genericName, index on quantityInStock.
Orders: Index on customerId, descending index on orderDate.
Payments: Index on supplierId, descending index on paymentDate.
ExpiryLogs: Index on expiryDate, supplierId, status.
Alternatives: Index on originalMedicineId, alternativeMedicineId.

5.4 Indexing Strategy

Indexes designed for query patterns:
- Email uniqueness enforcement for authentication
- Role-based queries for user management
- Supplier-based medicine lookups for supply chain
- Expiry date scanning for monitoring jobs
- Full-text search for medicine discovery
- Stock level alerts for JIT reordering
- Customer order history retrieval
- Payment reconciliation by vendor and date
- Expiry log filtering by status and supplier

5.5 Data Integrity Constraints

Application-level constraints enforced via Mongoose validation and API middleware:
- Code Number uniqueness and non-null validation
- Manufacture Date <= Expiry Date validation
- Required field validation on all entities
- Reference integrity for foreign keys (supplierId, customerId, medicineId)
- Role-based data isolation (shopId scoping for Shop Owners)
- Soft delete pattern (isActive flag) for audit trail

7. SECURITY DESIGN
================================================================================

7.1 Authentication and Authorization

JWT-based stateless authentication:
- Access tokens issued on login/registration with 24-hour expiry
- Tokens stored in localStorage (frontend) and sent via Authorization header
- Password hashing with bcryptjs (12 rounds)
- Role claim embedded in token payload (customer, shop_owner, super_admin)
- Shop Owner tokens include shopId for data scoping

Role-Based Access Control (RBAC):
- Middleware validates token and extracts role/shopId
- Route-level authorization: Super Admin routes require super_admin role
- Shop Owner routes require shop_owner role with matching shopId
- Customer routes require customer role with ownership validation
- API controllers enforce data isolation at query level

7.2 Data Protection

- HTTPS enforcement in production (corsOptions origin restriction)
- Environment variables for secrets (MongoDB URI, JWT secret)
- Input validation and sanitization via express-validator
- MongoDB injection prevention through Mongoose ODM
- Passwords never logged or returned in API responses
- Soft delete preserves audit trail

7.3 API Security

- Rate limiting (planned via express-rate-limit)
- CORS configuration: wildcard in development, restricted in production
- Helmet.js headers (planned)
- Request size limits
- Error handling without stack trace exposure in production
- Structured error responses without internal details

10.3 Migration Strategy

Java Backend Migration:
1. Implement Spring Boot services mirroring Express.js API contracts
2. Run both backends in parallel with feature flags
3. Migrate frontend API clients incrementally
4. Validate data consistency
5. Decommission Node.js backend

Database Evolution:
- MongoDB schema versioning via migration scripts
- Backward-compatible field additions
- Index optimization based on query analysis
- Potential sharding for multi-tenant scale
